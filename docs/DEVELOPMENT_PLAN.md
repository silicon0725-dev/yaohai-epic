# Godot 体素地形系统开发文档

-   **文档版本：** v0.1
-   **项目阶段：** 技术原型 / MVP
-   **目标引擎：** Godot 4.x（具体小版本在仓库中锁定）
-   **目标平台：** 先以桌面端为主，架构避免绑定单一平台
-   **文档状态：** 初始方案，待性能测试后冻结关键参数

## 1. 项目概述

本项目计划使用 Godot 开发一款受
Minecraft、复古物语、生存战争等作品启发的体素沙盒游戏。第一阶段不直接实现完整游戏，而是先建立可独立迭代的体素地形内核，为后续生存、采矿、建造、机械、NPC、Boss、维度与远征系统提供可靠的世界基础。

材质资源优先考虑开源、明确授权、允许在独立游戏中再分发的资源。材质包只是表现层资源，不应成为体素数据、地形生成或游戏规则的依赖。

### 1.1 当前目标

第一阶段需要验证：

1.  程序化生成一块可探索的体素地形。
2.  按需加载和卸载区块。
3.  以合并网格的方式渲染方块世界，而不是为每个方块创建一个场景节点。
4.  支持挖掘、放置与区块边界更新。
5.  为地形修改建立可持久化的存档方案。
6.  支持纹理图集和可替换材质资源。
7.  通过可重复的性能测试，为后续扩大视距和世界规模提供依据。

### 1.2 第一阶段不做什么

以下内容不属于最初 MVP：

-   完整的生存数值、营养、口渴、温度和季节系统。
-   完整的物品、工具、合成、背包和装备系统。
-   机械动力式的动力网络、机器和生产线。
-   NPC 招募、队伍管理与 Boss 战斗。
-   多维度、复杂洞穴生态和完整的世界事件系统。
-   大型编辑器、联网多人、复杂地形编辑工具。
-   在没有基准测试前进行过度的 SIMD、GPU 计算或多线程优化。

这些系统可以在体素内核稳定后逐步接入，避免第一阶段同时调试过多变量。

## 2. 核心架构原则

### 2.1 数据、规则与表现分离

-   **体素数据层**：保存每个位置的方块 ID 和必要的状态数据。
-   **世界规则层**：决定地形生成、方块放置限制、挖掘结果等。
-   **网格表现层**：将可见表面转换为 Godot 网格。
-   **物理层**：为玩家移动、射线检测和碰撞提供必要的几何。
-   **存档层**：保存世界种子、玩家修改与必要的世界状态。
-   **资源层**：将方块 ID 映射到纹理、材质、音效等资源。

渲染网格不是世界数据的事实来源。即使某个区块的网格被卸载，也必须能够根据数据重新构建。

### 2.2 稳定的语义身份

方块类型使用项目自有的稳定 ID，例如
`core:stone`、`core:dirt`，而不是把纹理路径或网格索引当作身份。数值 ID
可以用于运行时紧凑存储，但需要通过注册表映射到稳定名称。

存档中应保存稳定名称或带版本映射的数值
ID，防止后续重排注册表时破坏旧存档。

### 2.3 可替换的内容资源

材质包只能改变视觉表现，不应改变方块的基本身份和世界存档结构。未来可以替换贴图、调整
UV、增加材质变体，而不必重写地形生成和存档系统。

### 2.4 先建立可测量的正确性，再优化性能

每项优化都应有基准测试和正确性测试。不要仅凭主观感受决定区块大小、线程数量或网格算法。

## 4. 世界与区块数据

### 4.1 区块尺寸

第一轮对比测试使用以下候选值：

-   `16 × 16 × 16`
-   `16 × 16 × 32`

这里的高度是单个垂直区块的高度，不是整个世界高度。最终应根据生成成本、网格重建时间、可见面数量、碰撞更新成本和内存占用确定。

不要在尚未测量前将区块尺寸视为永久架构约束。应将其放入世界配置，并在创建存档时固定下来。

### 4.2 坐标约定

明确规定：

-   世界坐标采用整数体素格点。
-   一个方块占据一个整数坐标单元。
-   世界坐标到区块坐标使用正确的向下取整，特别处理负坐标。
-   区块内局部坐标范围为 `[0, chunk_size)`。
-   全部坐标换算集中在一个模块，禁止其他系统各自实现换算公式。

必须测试 `-1`、`-chunk_size`、`-chunk_size-1` 等负坐标边界。

### 4.3 方块数据

MVP
可以使用紧凑的整数数组保存方块类型。特殊状态（例如朝向、开关状态、容器内容、机器状态）不要一开始就为每个普通方块付出高额存储成本；可以采用按需的稀疏状态表。

初步数据模型：

``` text
ChunkData
- chunk_coord
- dimensions
- block_ids[]
- sparse_block_states
- generation_version
- dirty_flags
```

`dirty_flags`
至少区分数据是否修改、网格是否过期、碰撞是否过期、存档是否需要写回。

### 4.4 区块生命周期

建议定义明确状态：

``` text
UNLOADED
  -> QUEUED
  -> GENERATING
  -> DATA_READY
  -> MESH_QUEUED
  -> MESH_READY
  -> ACTIVE
  -> EVICT_PENDING
  -> UNLOADED
```

异步任务需要带有区块坐标和任务版本。若玩家快速移动导致区块已经不再需要，完成的旧任务不得错误地覆盖新状态。

区块卸载前，必须确保修改数据已保存或进入可靠的待保存队列。

## 5. 地形生成

### 5.1 确定性生成

世界使用固定种子。给定相同种子、生成版本和世界坐标，应得到相同的基础地形结果。

将生成算法版本写入存档。未来调整噪声参数、地层规则或生物群系算法时，不应假设旧存档可以直接使用新算法重建所有未修改区域。

### 5.2 MVP 地形范围

第一阶段只需要：

-   基础高度变化。
-   地表与地下的简单地层。
-   水平或垂直方向上的可配置噪声。
-   少量方块类型，例如空气、草方块、泥土、石头、基岩与水。
-   可重复的测试种子。

暂不追求完整的真实地质模拟、复杂洞穴、矿脉生成、气候模拟或生态链。

### 5.3 生物群系接口

先建立轻量的生物群系定义，不要将全部生成逻辑硬编码进一个大型脚本。生物群系至少能描述：

-   地形参数配置。
-   表层与地层规则。
-   温度或湿度等未来可扩展参数。
-   可生成的植被、矿物和结构规则引用。

第一阶段只需要少量测试生物群系，验证接口即可。

## 6. 网格生成与渲染

### 6.1 基础方案

先实现剔除被相邻不透明方块完全遮挡的面。每个区块生成一个或少量网格，而不是每个方块建立一个
`MeshInstance3D`。

Godot 的 `ArrayMesh`
可用于通过顶点、法线、UV、索引等数组构建程序化网格。MVP
可先用它实现正确版本，再比较面剔除与 Greedy Meshing 的收益。

### 6.2 网格生成阶段

1.  遍历区块方块数据。
2.  判断每个方块各方向的面是否需要显示。
3.  为可见面生成顶点、法线、UV 和索引。
4.  根据材质或渲染类别分组。
5.  在主线程或符合 Godot API
    线程安全要求的阶段创建、替换场景中的渲染资源。
6.  标记网格版本，防止旧任务覆盖新网格。

### 6.3 Greedy Meshing

不要把 Greedy Meshing 当作 MVP
的前置条件。先实现容易验证的可见面剔除算法，再用同一批测试区块比较：

-   网格生成耗时。
-   顶点与三角形数量。
-   CPU 时间和内存占用。
-   方块修改后的重建成本。
-   不同材质边界下的正确性。

如果收益明显，再把 Greedy Meshing 作为可切换实现。

### 6.4 区块边界

生成网格时必须读取相邻区块的边界方块。相邻区块尚未加载时，应采用明确且一致的临时策略；当邻区块数据到达后，重新标记相关边界网格。

修改区块边缘的方块时，除当前区块外，还要使相邻区块对应网格失效。

### 6.5 透明材质

MVP
首先只支持不透明方块。之后再分别处理透明或半透明方块，例如玻璃与水。不要把透明渲染、流体模拟和普通不透明网格混在第一版中。

## 7. 纹理与材质资源

### 7.1 Texture Atlas

第一版使用纹理图集，将多个方块贴图放在一张或少数几张纹理中。方块注册表为顶面、侧面、底面提供独立的纹理引用，允许草方块、原木等不同面使用不同贴图。

UV
生成必须考虑图集边界与过滤造成的纹理渗色。根据实际纹理尺寸和过滤模式测试边缘；必要时采用边缘填充、适当的
mipmap 策略或纹理数组等方案。

### 7.2 材质清单

建议建立类似以下的数据结构：

``` json
{
  "id": "core:stone",
  "render_type": "opaque",
  "textures": {
    "top": "res://assets/terrain/stone.png",
    "side": "res://assets/terrain/stone.png",
    "bottom": "res://assets/terrain/stone.png"
  },
  "collision": true,
  "occludes_neighbors": true
}
```

这只是概念示例，最终格式可使用 JSON、资源文件或自定义
`Resource`。逻辑属性与美术资源应当可以独立变更。

### 7.3 第三方资源与许可证

选择材质时应逐项确认：

-   许可证是否允许商业使用。
-   是否允许将素材打包进独立游戏。
-   是否要求署名、附带许可证或公开修改内容。
-   是否允许修改和重新分发。
-   资源包是否混用了其他作者的素材。
-   是否存在额外的品牌、商标或平台条款。

"免费""开源""可用于
Minecraft"并不自动代表允许在独立游戏中再分发。保留原始下载地址、作者、许可证文本、下载日期和修改记录。若许可不明确，只将其作为视觉参考，或自行制作替代资源。

## 8. 方块交互与物理

### 8.1 射线检测

玩家视线发出射线后，使用体素网格遍历算法（例如
DDA）确定被命中的方块及进入面。返回：

-   命中方块坐标。
-   命中面法线或方向。
-   命中距离。
-   放置方块时的目标相邻坐标。

这比为每个方块创建物理碰撞对象更适合大规模体素世界。

### 8.2 挖掘与放置

所有修改必须通过统一的世界 API，例如：

``` text
get_block(world_pos)
set_block(world_pos, block_id)
replace_block(world_pos, expected_id, new_id)
```

`set_block`
负责更新数据、标记相关网格和碰撞过期，并通知存档层。其他系统不应直接修改区块数组，否则容易漏掉网格重建或存档。

### 8.3 碰撞

MVP
先为区块生成合并碰撞形状。碰撞更新应与渲染网格更新分开调度，因为两者的更新频率和成本不同。

测试快速连续挖掘、区块边界修改和玩家贴近区块边缘移动时的正确性。不要默认每次修改一个方块都必须立即重建整个区块的所有资源；后续可根据测量结果增加局部更新或延迟合并更新。

## 9. 存档与版本迁移

### 9.1 存档原则

程序生成的基础世界可以通过种子与生成版本重建；玩家修改过的方块必须作为增量数据保存。为了防止生成算法更新破坏旧世界，存档还需记录版本和必要的区块数据。

建议的概念结构：

``` text
WorldSave
- format_version
- world_seed
- generator_version
- world_config
- player_state
- modified_chunks
- world_metadata
```

每个已修改区块可保存完整压缩数据，或保存相对于基础生成结果的修改记录。MVP
可以先采用更容易实现和验证的方式，再根据存档大小与读取速度进行优化。

### 9.2 原子写入

避免在覆盖唯一存档时因进程中断造成损坏。可先写入临时文件，完成并验证后再替换正式文件。定期保存与退出保存都应处理写入失败，并在调试日志中报告。

### 9.3 必测场景

-   修改方块后保存并重启。
-   卸载区块后重新加载。
-   负坐标区块的保存和读取。
-   存档中不存在的旧版方块 ID。
-   文件缺失、损坏或版本不兼容时的错误处理。
-   生成版本变更后的迁移策略。

## 10. 性能与线程策略

### 10.1 原则

地形噪声计算、区块数据生成和网格数组构建可以作为后台工作候选，但必须遵守
Godot
对场景树和渲染资源的线程安全约束。不要直接在工作线程任意创建或修改场景树节点。

建议采用"后台计算、主线程提交"的模式：

1.  主线程确定任务与版本号。
2.  工作线程生成纯数据或网格数组。
3.  主线程检查任务是否仍然有效。
4.  主线程创建或替换需要引擎对象的资源。
5.  完成后更新区块状态。

### 10.2 调度优先级

优先级可按以下顺序开始：

1.  玩家当前所在区块。
2.  玩家视野前方的区块。
3.  近距离邻接区块。
4.  视距内其他区块。
5.  预加载区块。

加载和网格构建需要限流，避免玩家快速移动时大量任务同时完成，造成主线程卡顿。

### 10.3 基准测试

建立固定种子和固定操作脚本，至少记录：

-   首次进入世界耗时。
-   一定数量区块的生成时间。
-   网格构建时间。
-   平均与峰值帧时间。
-   活跃区块数、网格顶点数和碰撞对象数。
-   内存使用趋势。
-   挖掘与放置后的网格更新耗时。
-   存档写入与读取耗时。

性能目标应先在目标硬件上测量，再制定数字化预算。不要在没有目标硬件和基准场景的情况下承诺固定
FPS。

## 11. 测试策略

### 11.1 单元测试

-   世界坐标与区块坐标互相转换。
-   负坐标取整与边界换算。
-   区块数组索引。
-   固定种子生成确定性。
-   面剔除的正确性。
-   区块边界修改的失效传播。
-   方块修改后数据与网格状态一致。
-   存档往返一致性。

### 11.2 集成测试

-   创建世界并生成初始区块。
-   玩家挖掘、放置方块。
-   离开后区块卸载，再次靠近并加载。
-   保存、退出、重新启动并恢复世界。
-   连续快速移动时没有旧任务覆盖新状态。
-   区块边缘的方块修改不会留下可见裂缝。
-   材质资源缺失时能报告错误并使用明确的回退策略。

### 11.3 手工验收

MVP 通过条件：

-   可以在小型体素世界中行走。
-   可以挖掘和放置方块。
-   区块加载、卸载和边界更新正确。
-   贴图没有明显错位或图集串色。
-   保存后重新启动，玩家改造的世界仍然存在。
-   性能数据可以重复测量。
-   日志能定位生成、网格、碰撞和存档错误。

## 12. 分阶段实施计划

### 阶段 A：最小体素原型

1.  建立 Godot 项目和版本锁定。
2.  定义坐标、方块 ID 和区块数据。
3.  生成一个固定大小的测试地形。
4.  使用 `ArrayMesh` 生成可见面。
5.  使用简单材质图集显示不同方块。

**交付物：** 能显示静态体素地形的原型。

### 阶段 B：交互

1.  加入第一人称测试控制器。
2.  实现体素 DDA 射线检测。
3.  实现挖掘和放置。
4.  更新受影响的网格和碰撞。
5.  处理区块边缘更新。

**交付物：** 可以自由修改的体素测试场景。

### 阶段 C：区块化与流式加载

1.  引入区块管理器。
2.  按玩家位置加载和卸载区块。
3.  引入任务队列和过期任务检查。
4.  加入加载优先级与工作预算。
5.  完成区块边界的正确处理。

**交付物：** 可持续探索、按需加载的程序化世界。

### 阶段 D：存档

1.  保存世界种子和生成版本。
2.  保存玩家修改过的区块。
3.  实现安全写入和读取。

## 13. 主要风险与应对

  风险                     应对措施
  ------------------------ ------------------------------------------------
  区块边界出现裂缝         将邻区块边界数据纳入网格构建，并测试边界修改
  地形生成导致卡顿         后台计算纯数据、主线程提交资源、限制每帧工作量
  每次挖掘都重建过多网格   先测量，再采用合并更新或局部重建
  存档与生成算法不一致     保存生成版本，使用增量修改与迁移机制
  材质包授权不允许再分发   逐项核验许可证，保存来源与许可记录
  太早加入复杂玩法         将生存、工业、NPC 与 Boss 放到体素内核稳定之后
  过早追求最优算法         先建立正确性测试和可重复基准，再决定是否优化

## 14. 当前需要冻结与暂缓的决策

### 现在可以确定

-   体素数据与渲染网格分离。
-   方块使用稳定语义 ID。
-   使用区块管理，不为每个方块创建独立节点。
-   使用统一 API 修改世界。
-   材质资源可以替换。
-   存档记录生成版本和玩家修改。
-   所有关键优化都需要基准测试。

### 暂缓决定

-   最终区块尺寸与世界高度。
-   是否需要 C#、GDScript、GDExtension 或自定义原生模块。
-   是否采用 Greedy Meshing、局部网格更新或更复杂的 GPU 路线。
-   流体、透明材质和动态光照的完整实现。
-   无限世界的最终存储格式。
-   多人同步、世界分片和服务器权威模型。

这些决定应由 MVP
的性能数据与未来玩法需求推动，而不是预先增加不必要的复杂度。
